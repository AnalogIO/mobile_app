# Login

Authentication via magic links, including registration for new users.

## Registration flow

- The user enters their email on `/login`. The backend always responds with `204`; it never reveals whether the email is registered.
  - Existing account: "Login to Analog" email with `.../login/auth/{token}`.
  - New email: "Welcome to Analog" email with `.../register/{token}`.
- `/register/:token` opens `RegisterScreen`. The token is single-use and already identifies the email address, so the screen only asks for name and study programme (using the settings feature's `ProgrammesCubit` through its public barrel). It never asks for a password.
- `AuthCubit.completeRegistration` returns a `Failure` to the caller instead of emitting `AuthFailure`. This keeps the registration screen open so the user can fix their details or request a new link. On success it stores the tokens and emits `AuthAuthenticated`, which makes `AuthNavigator` enter the app.
- Android's intent filter in `android/app/src/main/AndroidManifest.xml` must keep the `/register/` path prefix in sync with the `register/{token}` link generated by `analog-core`.

**Known limitation:** the legacy `POST /api/v2/account` and `POST /api/v2/account/email-exists` endpoints can still be used to probe whether an email is registered. They exist for the old app and should be removed/restricted when it is retired; the magic-link endpoints above do not leak account existence.

## Caveats

- Auth flow, not a fetch: `AuthCubit` states are named after the authentication lifecycle (`AuthAuthenticated`, `AuthEmailSent`, ...), not the `<Feature><Verb>` fetch pattern.
- `AuthNavigator` (a widget, not a screen) drives navigation, shows the loading overlay during `AuthLoading` and shows a snackbar on `AuthFailure`. Failure recovery happens here: it navigates to `/login` where the user can simply try again.
- The login screens intentionally use their own `Scaffold` layout instead of the shared `Screen` widget.
- `AuthCubitHandle` breaks the dependency cycle between the HTTP layer and `AuthCubit`: `TokenRefreshAuthenticator` is constructed before the cubit exists, so both share this handle and calls are queued until the cubit binds.
